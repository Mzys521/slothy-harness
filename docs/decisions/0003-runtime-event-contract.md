# 0003 运行时事件契约与分发边界

## 背景（Context）

0.1.0 的 Runtime 已经能运行完整的模型与工具循环，但运行过程没有对外通知接口：调用方只能在结束后读取 `Run` 状态。界面、日志和持久化因此必须侵入执行逻辑，或者只能轮询状态，无法知道“什么时候发生了什么”。

同时，事件天然会跨越运行时、日志和界面三方。如果观察者的异常能够回传，一次运行的结果就会被监控代码改变；如果事件负载直接带上原始异常或工具参数，密钥、完整路径和工具入参会顺着事件泄漏到界面与日志。

## 决策（Decision）

- 在 `core/events` 定义与提供方无关的事件分类：生命周期、模型、工具、状态/策略、观测五类，全部继承 `RunEvent`。
- 事件只由两处发出：`Run` 的既有状态迁移，以及 `AgentRunner` 的模型、工具调用边界。`Run` 与运行器共享同一个 `EventRelay`，整次执行使用同一个序列号空间。
- 事件负载只包含标识、计数、状态、耗时和错误分类，不包含密钥、未经筛选的工具参数、工具结果原文和内部异常堆栈。
- 核心层只依赖 `EventSink` 协议（`notify(event)`），并提供 `EventBus`（按类型订阅）与 `RunTimeline`（按顺序记录）两个最小实现。界面、日志、持久化的实现位于外层。
- 观察者异常在 `publish` 与 `EventBus.notify` 处被隔离并记入 `EventBus.failures`：不重试、不重新抛出、不影响运行结果。
- 同一次 Run 只产生一个 Run 级终态事件；进行中的步骤在取消、总时限或步骤时限生效时先写出 `StepEnd`。
- 错误分类由核心层定义：`RunStateError` 与 `RunCheckedError` 的子类各自提供稳定的 `error_code`，事件只携带该分类和异常类名。

## 理由（Reason）

- 事件产生点与状态迁移点重合，事件顺序天然等于状态顺序，不需要额外的状态镜像逻辑。
- 单一中继保证序列号连续，观察者可以据此判断事件是否丢失或乱序。
- 只依赖协议使 Core 保持框架无关，同时让运行器可以在没有接收端、或接收端损坏的情况下正常运行。
- 分类式的错误信息足够定位问题（哪个环节失败、属于哪一类），又不把提供方请求细节写进事件。

## 备选方案（Alternative）

- 让 `Run` 持有观察者列表并直接调用回调：实现更少，但观察者异常会直接改变运行结果，且状态对象会变成事件总线。
- 在运行器里集中构造全部事件、`Run` 完全不发事件：事件顺序需要人工复制状态机，容易被后续改动改错。
- 事件携带原始异常对象或工具参数：便于调试，但会把密钥与本地路径带到界面和日志，且要求观察者理解内部类型。
- 观察者异常向上抛出：可以让故障尽早暴露，但违反“监控不改变运行结果”，一次日志故障就会中断用户任务。

## 影响（Consequence）

- `AgentRunner.run` 新增可选关键字参数 `events`；`Run` 新增可选字段 `events` 与 `step_timeout_seconds`。不传事件时行为与 0.1.0 完全一致。
- `Step` 新增 `started_at`、`finished_at`、`duration_ms`；`StepTimeoutError`、`StepLimitExceededError`、`RunStateError` 在 `core/runtime` 导出。`StepLimitExceededError` 继承 `RuntimeError`，原有 `Exceeded max steps` 语义与消息保持不变。
- 步骤级时限只在模型与工具调用边界检查，与总时限一样属于协作式中断；同步调用进行中无法被强制打断。
- 事件投递失败只会记录在 `EventBus.failures`，因此监控故障不会被自动发现，需要外层主动检查该列表。
