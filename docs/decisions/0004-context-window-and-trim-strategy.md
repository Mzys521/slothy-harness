# 0004 上下文窗口与裁剪策略

## 背景（Context）

运行器在本次调用内维护消息列表，每轮工具调用都会追加助手消息和工具结果，列表只增不减。没有预算控制时，长任务会一直增长到提供方的上下文上限并直接失败；而 `ContextCompressed` 事件在 0.1.0 之后只有契约、没有发射方。

裁剪本身有几个容易做错的地方：不能把系统提示裁掉；不能只保留工具结果而丢掉对应的助手消息（请求结构会不合法）；核心层不引入分词器或具体提供方 SDK，因此拿不到精确令牌数。

## 决策（Decision）

- 在 `core/context` 实现 `ContextWindow`：保存系统提示与对话消息，按令牌预算裁剪，并在裁剪时返回 `CompressionRecord`；运行器据此发出 `ContextCompressed`。
- 令牌规模由 `TokenEstimator` 协议估算，默认实现 `HeuristicTokenEstimator` 按字符估算（ASCII 每 4 字符约 1 个令牌，非 ASCII 每字符 1 个令牌）。估算只用于判断是否需要裁剪，不用于计费或对外报告。
- 裁剪策略为 `trim_oldest`：丢弃最早的消息，直到估算规模进入预算。两条硬约束是“不切断尾部工具结果与其助手消息的配对”和“至少保留最新的一条消息”。
- 系统提示单独保存并永不裁剪；当对话消息全部被裁掉时，请求只包含系统提示。
- 若最小尾部本身就超出预算，就保留它并照常记录一次裁剪：丢弃最新消息会让下一次请求失去最新上下文，比超出预算是更糟的结果。因此预算是保守目标，不是硬性上限。
- 没有实际裁掉任何消息时不发出事件，避免每次请求都产生一条零裁剪记录。
- `ContextWindow` 由调用方注入 `AgentRunner(context=...)`，或仅给出 `token_budget`；不注入时使用 `DEFAULT_TOKEN_BUDGET`，因此不传参数的调用与之前行为一致。

## 理由（Reason）

- 裁剪决策留在 Core，事件由运行器发出，观察者不需要理解窗口内部结构就能得到“裁剪了多少、少了多少令牌”。
- 使用协议而不是分词器，让 Core 继续保持提供方无关；具体提供方将来可以提供精确估算器。
- 硬约束对应请求结构的合法性，把“保留哪些消息”写成可测试的规则，而不是隐式行为。

## 备选方案（Alternative）

- 在核心层引入具体分词器：估算更准，但会把提供方 SDK 依赖带进 Core。
- 摘要式压缩（调用模型总结旧消息）：压缩率更高，但需要额外模型调用、额外成本，并会引入“总结失真”这类新的失败模式；本阶段不做。
- 达到上限就报错：实现最少，但长任务直接失败，与可观察运行时和可恢复性的目标相反。
- 由外层维护消息列表并自行裁剪：Core 的 `AgentRunner` 会失去对请求规模的控制，事件也无法表达真实裁剪。

## 影响（Consequence）

- `AgentRunner` 新增可选参数 `context` 与 `token_budget`；`run` 每次调用都从空窗口开始，因为当前每次执行只维护本次调用的对话消息。跨 Run 的会话上下文仍需单独设计。
- 估算不精确，因此预算只能作为保守目标：估算偏小会晚一点裁剪，偏大则会提前裁剪。
- `ContextCompressed` 的 `preview` 只包含被裁掉的文本消息（按 120 字符截断），不包含工具结果内容。
- 裁剪发生一次后不会重复发出相同事件：只有再次裁掉消息时才会产生新事件。
